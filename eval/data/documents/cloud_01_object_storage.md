# Object Storage for Application Files

Object storage keeps files as independent objects inside named buckets. Each object has content, metadata, and a key that acts like its path. This model works well for uploaded PDFs, images, and audio because the application does not need to manage a traditional filesystem tree.

A storage service usually returns a URL or object identifier after an upload. The application can save that identifier in its database and retrieve the original file later. Object storage is designed for durability and can store many large files without filling the application server's local disk.

For a student application, useful metadata includes the original filename, media type, upload time, owner, and checksum. A checksum helps detect duplicate uploads and verify that a downloaded file has not changed.

A reliable upload flow validates the file, streams it to a bucket, calculates a checksum, and stores the object key in a database only after the upload succeeds. Large files can use multipart upload so a failed network request does not require starting over. Object keys should be generated by the application instead of being built directly from untrusted filenames, which avoids collisions and confusing path-like names.

Object storage is not a replacement for a relational database. The bucket stores bytes, while the database can store ownership, permissions, document status, extraction results, and relationships between files. Access should be private by default, with short-lived signed URLs when a user needs a download. Keeping original objects immutable also makes it safer to rerun OCR, chunking, or embedding experiments later.
